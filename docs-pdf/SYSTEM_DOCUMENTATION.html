1. System Overview

What is PetAdopt+?

PetAdopt+ is a web application for pet care services. It brings three main services into one place:

ServiceWhat users can do
Pet AdoptionBrowse pets in the shelter, apply to adopt, track application status
Pet ShopBuy food, toys, and accessories online (cart, checkout, Khalti or cash on delivery)
Pet HostelBook a room for their pet when they travel (check-in / check-out dates, online payment)

Who uses it?

RoleWho they areMain tasks
User (customer)Pet owners / adoptersSign up, shop, adopt, book hostel, view orders & adoptions
AdminSystem managerDashboard, manage pets, products, rooms, staff, orders, adoptions
StaffHostel workersView rooms and bookings, update booking status

Purpose of the system

  • Help a pet shelter manage adoptions digitally
  • Run a small online pet store with inventory and payments
  • Run a pet boarding (hostel) with room availability and bookings
  • Give admins reports (revenue charts, sales, stats) for business decisions

Think of the system as three layers that talk to each other:

``

┌─────────────────────────────────────────────────────────────┐

│ React app — runs at http://localhost:5173 │

│ Pages: Shop, Login, Admin Dashboard, Hostel, etc. │

└───────────────────────────┬─────────────────────────────────┘

│ HTTP requests (fetch)

│ JSON data + Bearer token for login

▼

┌─────────────────────────────────────────────────────────────┐

│ BACKEND SERVER (Brain of the system) │

│ Node.js + Express — runs at http://localhost:4000 │

│ Routes → Controllers → Database models │

└───────────────────────────┬─────────────────────────────────┘

│ Mongoose

▼

┌─────────────────────────────────────────────────────────────┐

│ DATABASE (MongoDB Atlas — cloud) │

│ Collections: users, pets, products, orders, bookings, … │

└─────────────────────────────────────────────────────────────┘

External services (used when needed):

• Cloudinary — stores pet/product/room images

• Gmail (Nodemailer) — verification & notification emails

• Khalti — online payments for orders and hostel bookings

`

How frontend and backend connect

  1. User clicks something in the browser (e.g. “Login”).
  2. React calls the backend, for example:

POST http://localhost:4000/api/auth/login with email and password.

  1. Backend checks the database and sends back JSON, for example:

{ success: true, data: { user, token } }.

  1. Frontend saves the token in localStorage and uses it on later requests:

Authorization: Bearer <token>.

  1. Protected pages send this token; backend verifies it before allowing access.

Example: Loading the shop products

  • Frontend: GET http://localhost:4000/api/products
  • Backend: reads products from MongoDB, returns list as JSON
  • Frontend: draws product cards on screen

4. Feature-by-Feature Breakdown

4.1 Cloudinary (Image storage)

What it is: Cloudinary is an online service that stores and serves images. Your app does not store large image files in MongoDB — only the image link (URL) is stored in the database.

#### Upload flow (step by step)

  1. Admin picks an image when adding/editing a pet, product, or hostel room.
  2. Frontend sends the image file to:

POST /api/upload

(field name must be image)

  1. Multer (middleware) saves the file temporarily in backend/uploads/ with a unique filename.
  2. UploadController calls Cloudinary and uploads the file to folder petadopt on Cloudinary.
  3. Cloudinary returns:

- secure_url — link to view the image

- public_id — ID used to delete the image later

  1. Frontend puts secure_url into the form and saves the pet/product/room.
  2. Database stores only the URL string in the image field.

#### Where images are stored

LocationWhat is stored
Cloudinary cloudActual image files (in folder petadopt)
MongoDBText URL only, e.g. https://res.cloudinary.com/your-cloud/image/upload/...
backend/uploads/Temporary files during upload (not the permanent store)

#### How images are shown to users

  • Pet list, shop, product details, hostel rooms read image from the database.
  • The browser loads the image directly from Cloudinary’s URL (like any normal website image).

#### Delete flow

  • DELETE /api/upload/:publicId removes the image from Cloudinary.
  • Used when admin replaces or removes images.

#### Configuration

Credentials live in backend/.env:

  • CLOUDINARY_CLOUD_NAME
  • CLOUDINARY_API_KEY
  • CLOUDINARY_API_SECRET

If these are missing, upload will fail but the rest of the app still runs.

4.2 Product discounts

#### How discount is stored

On each product in the database:

FieldMeaningExample
priceNormal price in Rs1000
discountPercent off (0–100)20 means 20% off

#### How the offer price is calculated

Formula:

`

Offer price = round( price × (1 - discount / 100) )

`

Example: Price = Rs 1000, Discount = 20%

→ Offer price = 1000 × (1 - 20/100) = 1000 × 0.8 = Rs 800

The backend model also has a virtual field offerPrice that uses the same formula.

#### Where discount is set

  • Admin → Inventory Management → Add/Edit Product → “Discount %” dropdown.

#### How the user sees it

PageWhat user sees
ShopOld price crossed out, new price in orange, “20% OFF” badge
Product detailsSame styling
CartUses discounted price per item (saved when adding to cart)
CheckoutSubtotal and total use cart prices

#### How it works in the cart

When user clicks “Add to cart” on the shop:

  1. Frontend calculates effective price with the same formula.
  2. Cart stores price = discounted price and keeps originalPrice for display.

Note for viva: Checkout sends subtotal and totalAmount from the cart (with discounts). The backend also rebuilds line items from the database using each product’s catalog price field when creating the order. Totals on the order often follow what the frontend sent; line-item prices in the order record reflect the database price at order time.

4.3 Admin dashboard — monthly revenue bar graph

#### What the chart shows

A bar chart with 12 bars (Jan–Dec) for the current year.

Each bar height = total revenue for that month from:

  • Shop orders (delivered + paid)
  • Hostel bookings (not cancelled)

#### What data is fetched

On page load, the admin dashboard calls three APIs:

APIPurpose
GET /api/dashboard/statsSummary cards (users, pets, revenue total, etc.)
GET /api/dashboard/revenueMonthly bars data
GET /api/orders/product-salesPie chart — top products sold

#### How monthly revenue is processed (backend)

GET /api/dashboard/revenue (in DashboardController.js):

  1. Takes year (default: current year).
  2. Finds orders where:

- status = Delivered

- paymentStatus = Paid

- Created in that year

  1. Only counts order line items whose product still exists in inventory (deleted products are excluded).
  2. Finds hostel bookings where status is not Cancelled.
  3. Groups money by month (1–12).
  4. Returns array like:

`json

{

"success": true,

"data": [

{ "month": "Jan", "orders": 5000, "bookings": 2000, "total": 7000, "orderCount": 3, "bookingCount": 1 },

{ "month": "Feb", "orders": 0, "bookings": 1500, "total": 1500, ... }

]

}

`

#### How it is displayed (frontend)

AdminDashboard.jsx:

  1. Saves revenueData from the API.
  2. Uses Chart.js to draw a bar chart.
  3. Each bar uses m.total (orders + bookings).
  4. Clicking a bar calls GET /api/orders/revenue/:month/:year and shows tables of successful orders and paid bookings for that month.

#### Pie chart (product sales)

  • Data from GET /api/orders/product-sales.
  • Counts quantity sold per product from paid/delivered orders.
  • Uses current product name from inventory (not old names on orders).
  • Skips deleted products.
  • Shows top products in a pie chart.

4.4 Other major features

#### Pet adoption

  • Public browse; apply when logged in.
  • Application statuses: pending, approved, rejected, withdrawn.
  • Admin can approve with pickup details or reject with notes.
  • Emails sent on submit, approve, reject.

#### Pet hostel

  • Admin creates rooms (type, price per day, facilities, image).
  • User picks dates; system checks availability.
  • Booking statuses: Pending → Confirmed → Checked-In → Checked-Out (or Cancelled).
  • Payment: Cash or Khalti.
  • Staff/admin update status; emails on status change.

#### Online payments (Khalti)

  • User chooses Khalti at checkout or hostel booking.
  • Backend creates payment session via Khalti API.
  • User pays on Khalti website, returns to your app.
  • Backend verifies payment, then marks order/booking as paid and updates stock.

#### Product reviews

  • Logged-in users can rate and comment on products (1 review per user per product).
  • Shown on product details page.

#### Hostel room reviews

  • Logged-in users can review hostel rooms after staying.
  • Shown on hostel room details page.

#### Staff management

  • Admin creates staff accounts (role = staff).
  • Staff log in to staff dashboard, view rooms and bookings, update booking status.

#### Email notifications

Used for: signup verification, password reset, order confirmation, order status updates, adoption updates, hostel booking confirmation and status updates.

#### Session checking

SessionChecker on the frontend watches if the login token is still valid and can log the user out if expired.

7. Authentication Flow

Signup

  1. User fills name, email, password on /signup.
  2. Backend checks password strength (8+ chars, upper, lower, number, special).
  3. Backend creates user with isVerified: false.
  4. 6-digit code emailed (valid 10 minutes).
  5. User enters code on /verify-email.
  6. Backend sets isVerified: true.
  7. User can now log in.

Login

  1. User submits email + password.
  2. Backend compares password (encrypted).
  3. If email not verified → error with needsVerification: true.
  4. If OK → JWT token created (default expiry 7 days).
  5. Frontend stores token and user in localStorage.

Protected routes (frontend)

ProtectedRoute wrapper checks:

  1. Is there a valid token in localStorage?
  2. If route needs a role (admin/staff), does user’s role match?
  3. If not → redirect to login or correct dashboard.

Protected routes (backend)

protect middleware:

  1. Reads Authorization: Bearer <token>.
  2. Verifies token with JWT_SECRET.
  3. Loads user from database.
  4. Attaches user to req.user for the controller.

Extra middleware:

  • adminOnly — only role === 'admin'
  • staffOrAdmin — staff or admin (hostel operations)

Example: Calling a protected API

`javascript

fetch('http://localhost:4000/api/orders/my-orders', {

headers: {

'Authorization': 'Bearer ' + localStorage.getItem('token')

}

})

`

8. Error Handling

How the backend handles errors

Most controllers use try / catch:

  1. Try to do the work (database, email, payment).
  2. If something fails → catch block runs.
  3. Server sends JSON with success: false and a message humans can read.
  4. HTTP status code tells the type of error:
StatusMeaningExample
400Bad request / validationMissing email, weak password
401Not logged in / bad tokenNo Bearer token
403Not allowedUser trying to open admin page
404Not foundProduct or order does not exist
500Server errorDatabase down, unexpected crash

Form validation errors

Routes like signup use express-validator + validate middleware.

Response example:

`json

{

"success": false,

"message": "Validation error",

"errors": [

{ "field": "email", "message": "Please provide a valid email" }

]

}

`

How the frontend handles errors

  • Checks response.success from API.
  • Shows alert() or on-screen message with data.message.
  • Login page handles needsVerification to send user to verify email.
  • ProtectedRoute redirects if session expired.

MongoDB connection errors

If database cannot connect on startup:

  • Console shows: MongoDB connection error
  • Process exits (server stops)
  • Fix: check MONGODB_URI in .env and internet connection.

Port already in use

  • Message: Port 4000 already in use
  • Fix: run npm run kill-port in backend folder, then npm run dev again.
